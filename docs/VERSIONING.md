# 项目版本

项目从 `v1.0` 起，`VERSION` 保存不带 `v` 的数字。重大更新由维护者判断，递增次版本号并清零补丁号：`v1.0.2` → `v1.1` → `v1.2`。小修复、文档及其他较小改动递增补丁号：`v1.0` → `v1.0.1` → `v1.0.2`；进入 `v1.1` 后为 `v1.1.1`、`v1.1.2`。数字不按小数处理，`v1.1.9` 后为 `v1.1.10`。

提交钩子默认按小改动递增。重大更新时，在提交前手动将 VERSION 改为下一次版本号（例如 1.1）并暂存；钩子会保留该版本，不再额外递增。由 Codex 维护时根据实际变更判断，不以文件数量或提交消息关键词自动推断重大程度。定时构建与重跑不属于提交，不递增项目版本。

维护者首次克隆后执行 `git config core.hooksPath .githooks`，并确保 `python` 可用。也可通过 `git config bridge.pythonPath <Python可执行文件绝对路径>` 指定解释器。Git 不会将 hooks 配置自动传播给其他克隆，网页提交也不会执行本地 hook；这些提交必须自行更新 VERSION。默认不要绕过版本递增。维护者明确要求同版本修订并替换原 Release 时，可为该次提交跳过仅负责版本递增的钩子，保持 VERSION 不变，并固定替换目标。仅重打包时必须验证复用的运行文件原字节不变；涉及源码修复时必须重新完成正式构建与必要回归，不能沿用旧构建通过结论。两种情况均保留旧附件证据，在原 Release 记录新提交、配方、构建实例和附件校验值。

提交钩子只更新并暂存 VERSION，不暂存其他文件；VERSION 有未暂存内容时会阻止提交。版本更新进入同一个提交，不额外生成版本提交。提交失败后重试不会再次递增。

Release 标题显示项目版本，附件和发布 tag 默认在项目版本后保留 Nightly 构建标识，区分同一提交的不同上游版本和强制重建，避免覆盖旧附件。明确授权的原位修订保持指定原 Release/tag 身份，不另发版本；当前构建身份以新的发布收据为准，不能把原 tag 名中的旧配方和运行号当作修订后附件身份。项目版本不是稳定性认证，游戏测试范围仍以发布说明为准。
